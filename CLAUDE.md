# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

candy-localhost is a lazy-loaded dev server orchestrator. It spawns local development servers on-demand when you visit `.localhost` domains, auto-detects ports from process output, and provides MCP tools for AI integration.

## Commands

```bash
# Development with auto-reload
bun run dev

# Run daemon once
bun run daemon

# Run MCP server (for AI tool integration)
bun run mcp

# Install as systemd service (also builds the portal SPA as you, never as root)
sudo npm run install-service

# The portal SPA (web/, its own package with react + react-dom): install, build, watch, test
bun run web:install && bun run web:build
bun run web:dev        # rebuilds web/dist on save; the running daemon serves it on the next reload
bun run test:web       # web tests; `bun test` at the root ignores web/**
```

## Architecture

Two main files (plus `fn-*.ts` for functions, see Functions below):
- **daemon.ts** - Main control server running on `localhost:9999`. Handles process spawning, Caddy reverse proxy management, port detection, and HTTP API.
- **mcp.ts** - MCP server exposing tools for AI clients via JSON-RPC over stdio. Authenticates with daemon using a bootstrap secret.

### Data Flow

1. User visits `<name>.localhost` → Caddy routes to daemon
2. Daemon spawns server process with PTY (`Bun.Terminal`)
3. Port detection scans stdout/stderr for 10 seconds using regex patterns
4. Single port detected → auto-bind route; multiple ports → selection UI
5. Daemon updates Caddyfile and reloads Caddy

### Key State (in-memory maps)

- `processes: Map<string, ManagedProcess>` - Running servers
- `serverConfigs: Map<string, ServerConfig>` - All configurations (persisted to `~/.config/candy/servers.json`)
- `routes: Map<string, number | string>` - Name → port mappings
- `portals: Map<string, Portal>` - Active Cloudflare tunnels

### Process States

`starting` → `running` → `dead` or `errored`

Servers auto-kill after 1 hour of inactivity unless they have active tunnels. Activity = Caddy access-log lines (including bound domains), open TCP connections to the server's port, or daemon-proxied requests. Servers that called SDK `setIdling()` survive until memory is tight. Logic lives in `activity.ts` (`idleVerdict`), wired up in daemon.ts `killIdleServers`.

### Cron

`ServerConfig.cron` holds the jobs candy.json declares (`"cron": [{ tag, schedule, args?, timeout? }]`, manifest.ts; the tag is the job name). `applyManifest` (daemon.ts) rewrites them whenever the file is read. candy.json is read only at a site's start (`siteManifest(config, 'check')` in `launchSpec`) and on a reload (`'force'`: `candy reload` → `POST /config/reload`, or the SDK); every other caller gets the cached copy with no stat. The SDK reads (`cronJob()`) and can ask for a re-read after the app edits its own file (`reloadServerConfig()` → `POST /runtime/reload-config` → `siteManifest(config, true)`); there is no `/sdk/cron`. A function's jobs are its untagged `crons` plus the tagged entries (`cronJobsFor`), run as `--scheduled <expr> [--tag <tag>]` so `scheduled(controller)` sees `controller.tag`. A run is `config.cmd "$@"` with the job's args as argv (see `cron.ts`, `launchSpec(config, cron)`); never build shell text from args.

## Functions

candy-functions run Workers-style modules (`export default { fetch, scheduled }`, Hono apps as is) as `ServerConfig.fn = { entry, deploy?, hot?, max?, log? }`. Full design and the binding module contracts: `FUNCTIONS_DESIGN.md`.

- **Functions never listen on a port or a socket of their own.** Don't add `Bun.serve`, port detection or Caddy upstreams for them. Caddy sends their hosts to the daemon (`reverse_proxy localhost:9999`, route target `{ fn: name }`), and the daemon dispatches by `Host`.
- **Transport**: the daemon listens on `/run/candy/fn/<name>.sock` (user mode `$XDG_RUNTIME_DIR/candy/fn/`), mode 0600, bind-mounted into the sandbox. The instance dials in with `CANDY_FN_TOKEN`. Frames are `u32 len, u8 type, u32 streamId, payload` (`fn-protocol.ts`), many requests multiplexed per connection. HELLO marks the instance ready (replaces port detection).
- **Lifecycle**: TTL 0. A request spawns an instance, waits for HELLO, dispatches. The instance sends BYE and exits when nothing is in flight and `waitUntil` is settled. `hot` instances stay up and are respawned; `max` caps the pool (`fn-pool.ts`). `ttl` and `killIdleServers` don't apply. Cron runs `fn-host.ts <entry> --scheduled <expr>`, args fixed by candy.
- **Files**: `fn-protocol.ts` (frames), `fn-dispatch.ts` (`FnConnection`, daemon side), `fn-pool.ts` (instances), `fn-host.ts` (the shim run inside the sandbox; `/usr/lib/candy/fn-host.ts` in root mode), `fn-config.ts` (`candy.fn.json` / `wrangler.*`), `fn-bindings.ts` (KV, D1), `fn-cron.ts` (`scheduled`, `ExecutionContext`), `fn-deploy.ts` (bundles), `fn-log.ts` + `fn-console.ts` (request log, per-request console), `fn-assets.ts` (Workers Static Assets: resolver, `_headers`, `_redirects`, `.assetsignore`, deploy snapshots).
- **Static assets**: routing order is `run_worker_first` patterns → `_redirects` → asset → the worker, or `not_found_handling` when there's no `main`. The daemon serves asset hits itself without spawning an instance; an assets-only function never starts a process. Surfaces decide that from `fn.hasWorker` (the cached routing state, so a pinned deploy's own worker and assets config), never from `fn.entry`, which is display only. Pattern matching (`run_worker_first`, `_redirects`, `_headers`) is regex-free and linear on the visitor's path; keep it that way. Request log rows carry `kind: "worker" | "asset"` and `rule`.
- **State**: KV/D1 SQLite and `deploys/<id>/` in the function's state dir (`/var/lib/candy/<name>`, user mode `~/.local/state/candy/fn/<name>`). Deploy snapshots are read-only in the sandbox; secrets from `envFile` are never written into them.
- **Request log**: `/var/lib/candy-daemon/fn-log/<name>.sqlite` (user mode `~/.local/state/candy/fn-log/`), written by the daemon from the frames it relays, never mounted into the sandbox. 24h retention, 256 MB cap, 64 KB bodies, header/field redaction. The function's user or a superuser (`mayChangeConfig`), and never on a public host.
- **API**: `/fn/add|settings|deploy|rollback|dev|deploys|instances|requests|request|tail|replay|kv|d1`. `/configs` entries carry `fn`. The bundle step runs as the function's user, never root.
- **Portal**: `fn` badge, Function panel (assets config with `run_worker_first`, assets-only badge, deploys, rollback, back to dev, hot/max/log, instances, Requests tab with kind + rule per row, live tail over `fetch` SSE and replay, KV/D1 Data tab) in the portal SPA's site pages (`web/src/pages/site/`).

## HTTP API Authentication

Spec: "Portal Login (PAM)" in `AUTH_DESIGN.md`.

- **`requestAuth(req)`** in daemon.ts is the only way to ask who a request is: `{ user, superuser, via: "portal" | "apikey" | "oauth", sessionId? } | null`. API keys (`X-Candy-API-Key`: CLI, SDK, local MCP) and public MCP tokens are always `superuser: false`. A portal login (`candy_portal` cookie, read only on portal hosts) gets `superuser` from `isSuperuser` (superuser.ts, sudoers, 60s cache) on every request; it is never stored. A passkey login of a sudoer is a superuser too, exactly like a password login (no step-up).
- **`ROUTE_TABLE`** (next to the control server) classifies every control route as `public`, `user`, `superuser` or `app` (a page of the portal SPA: GET only, no login, answered only on a portal host by the one app branch right after the guard; 404 anywhere else). One guard (`classifyRoute` + `guardRequest`, portal-auth.ts) runs before any route on portal and control hosts; a route missing from the table is a 404. Adding a route means adding a table line; `test/route-table.test.ts` reads both and fails otherwise.
- **Hosts**: site hosts (`<name>.localhost/.candy`, action hosts, bound domains) never reach the control API; they get pages and lazy start (`serveSitePage`), plus `siteAction`: tunnel status, a bounded startup excerpt of its own log while starting or crashed (from `ManagedProcess.logStart`, so only this run's output), and start/restart with the site token (`siteTokens`) minted into that page. With a site token, start only starts a stopped site (no `configId`: a site with several commands is started from the portal) and restart only an errored or dead one; the site's tokens end when it becomes running (`dropName`). Never `/process/port` or the full log. Shortcut hosts (`<name>.k|kill` stops, `<name>.p|portal` tunnels) only 302 to `https://portal.<tld>/go/kill|portal?name=` (user routes): a confirmation page on GET, the action on POST with the page token. Terminal input and registering link to the portal (`/?logs=<name>`, `/?add=<name>`). candy's own host (`candy.<zone>`, candy-host.ts), the public MCP host, function hosts and `/candy-auth/*`, `/candy/*` are handled before the guard.
- **User routes are user-scoped**: check `mayChangeConfig(auth, config)` / `mayUse(name)` (= `mayChangeName`: the name's config user, else `routeUsers`, else the owner) and filter every list by it. Superuser = portal-only sudoer. The owner (`CANDY_OWNER`) has no extra rights.
- **CSRF**: state-changing portal requests need `Origin` (or `Referer`) on a portal host (`sameOrigin`) and the page's `X-Candy-Token`. Page tokens (`PageTokens`) are minted only for a portal login and tied to its session id; max 2 valid per page (current + previous).
- **Login**: `/login`, `/auth/users`, `/auth/login`, `/auth/logout`, `/auth/me`. `attemptLogin` (portal-auth.ts) does PAM (`verifyPassword`, pam.ts, in a child process) with `LoginSlots` (one attempt per user and per IP, 4 helpers overall), the attempt counted before PAM and refunded on success, Fibonacci grudges per non-loopback IP, `SoftLockout` (capped 30s) per user and for loopback, and equal-time (4.5s), equal-body failures. All of 127/8 and ::1 is one address (`loginKeys`). Answers that checked no password are 429s, never "wrong password": the address lockout, the user's soft delay (`retryAfter`), and full slots (`busy, try again`). Sessions: `PortalSessions` (portal-session.ts), hashed cookie + hashed session secret, 24h idle / 7d max, 20 per user. `requestAuth` re-checks `loginUsers` (60s cache) on every request.
- **Session secret**: the cookie alone never authenticates (browsers share it with every port of the host). `/auth/login` returns `session`, which portal-login.html keeps in `localStorage`; every portal request sends it as `X-Candy-Session` (`SESSION_FETCH_PATCH` patches the page's `fetch`). Navigating to one of the remaining server-rendered portal pages (`PORTAL_PAGES`: OAuth and app consent, `/go/kill`, `/go/portal`) gets `public/portal-shell.html`, which re-requests the page with the header and `document.write`s it: page tokens never go out on a plain navigation. The portal SPA (`web/`, built to `web/dist`, served by `portal-app.ts` through fn-assets' `AssetServer` for `app` paths and `/assets/*` only) gets no token on a navigation: its static `index.html` holds nothing, and the SPA calls `POST /portal/boot` (`portalBoot` in app-auth-routes.ts; TOKENLESS, still `sameOrigin`; portal logins only, else 403) with `X-Candy-Session` for its first page token and who is looking. A missing or unreadable build is a 503 page that names no path or user (`PORTAL_UNBUILT` in the log); root mode serves only what the owner can read (`userCanRead`). `PORTAL_BUILD_STALE`: web/src newer than web/dist (30s timer). EventSource can't send headers, so portal streams use `fetch`. CORS: exact portal origins only (`isPortalOrigin`); `isPortalHost` refuses any port but 443.
- **Client IP**: `X-Forwarded-For` / `Cf-Connecting-Ip` only from our Caddy, which tags what it sends the daemon with a per-boot `X-Candy-Proxy` value (`tagDaemonUpstreams`, `clientIp`). Direct :9999 callers get their socket address. `markProxyHeaders` runs first on every request: it records `viaOwnCaddy`, deletes the tag, and deletes `X-Forwarded-*` / `Cf-*` from anyone but Caddy. Forwarders (`fnRequestHeaders`, `upstreamRequestHeaders`) delete it again.
- **Portal host**: `isPortalRequest` = a portal Host, and `X-Forwarded-Host` (from our Caddy) is the same host, so a bound domain whose upstream is the portal isn't the portal. Every response on the portal host carries `frame-ancestors 'none'`, `X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff` (`noFraming`); SPA pages also get the strict `PORTAL_APP_CSP` (portal-app.ts), which the daemon sets last.
- **Audit**: `auditLog` escapes control characters in every field. The actor is `auditActor(auth, X-Candy-Actor)` = `<user>:<label>` (`requestActor` in the control server); the header is only a label. Names can't start with `_` or `.`; `logFileFor` maps `_audit`/`_caddy` to the system logs (superusers) and a site name only to `<name>.log`.
- **Generated config**: every value written into the Caddyfile or cloudflared's YAML goes through `caddy-config.ts` checks (`isDnsLabel`, `isZoneName`, `isCaddyUpstream`, `checkBindings`, `cloudflaredYaml`); invalid bindings are dropped at load with `DOMAIN_BINDING_DROPPED`. `isCaddyUpstream` refuses this machine (`localhost`, `*.localhost`, `*.candy`, loopback, `ownAddresses()`) except the plain `localhost:<port>` / `127.0.0.1:<port>`. Blocks the daemon makes for itself carry `SYSTEM_BLOCK_MARK`; `dedupeSiteAddresses` keeps each address once (system first), and a skipped one is audited as `CADDY_SITE_SKIPPED`. `*.localhost` blocks get `bind 127.0.0.1 ::1` (`loopbackBind`). Bindings record `owner`; when their site is removed they're `orphaned`, still the owner's, and `boundToSomeoneElse` keeps others off the name.
- **candy.json** (`manifest.ts`): the site's manifest in its `cwd`, shared keys `auth`, `depends` and `publish` for servers and functions; a function's own keys live in the same file (`fn-config.ts`; `candy.json` is the only file read, `candy.fn.json` / wrangler files only produce a warning). The daemon never reads it as root: `siteManifest(config)` runs fn-tool op `manifest` as the config's user, re-checks the answer (`checkSiteManifest`) and caches by stat stamp; `refreshManifests()` (2s throttle) runs before the sign-in routes and on the 30s tick. A bad file throws from `launchSpec` ("Refusing to start"). `isAuthSite` needs `manifestNow(name)?.auth`. **depends**: `startDependencies` (in `spawnProcessNow`, `launchFnInstance`, `runCronJob`, always before `launchSpec`) walks `dependencyGraph`, refuses loops (`findDependencyLoop`) and other users' sites that aren't `publish`ed (superusers may depend on anything), then `startDependency` each. Holds are computed, not stored: `heldBy(dep)` = sites up now whose start recorded `dep` (`ManagedProcess.depends`, `fnDepends`), plus `holdGrace` (2 min after a start). `killIdleServers` skips a held site first; a held function gets hot >= 1 through `fnLimitsNow` until `releaseFnHolds`. A stop someone asked for goes through `stopDependents` then `stopSite` (dependents first; never idle stops or restarts). `spawnProcess` joins an in-flight start of the same name (`spawning`).
- **Function URLs and handlers**: candy.json `"handlers": ["http", "cron", "sub"]` (fn-config.ts, null when absent = everything). `syncFnUrl` (daemon.ts) routes a function only when handlers is absent or has `"http"`, or it has assets; otherwise it stores `fn.http: false` and drops the route. It runs from `applyManifest` and on add, deploy, rollback, dev and restart. `fn.http` shows in the fn summary; `/fn/add` returns `url: null`. candy never loads the module to find out.
- **Runtime records, events, service tokens**: every named launch gets a runtime record (`runtimeLaunch`, sdk-runtime.ts): `{ token, site, url, serviceKeys?, event? }` as the `candy-runtime` credential (sandboxed) or `CANDY_RUNTIME` in the spawn env, never argv (`SECRET_ENV_NAMES`). The token is the only credential of `/runtime/*` (table class `public`; loopback, not through Caddy, no `Origin`; `runtimeGrantFor`): a server's lives until its next start, other launches' until `launch.release()`. It names site + config + user and opens nothing else. Manifest keys `idle` (gates `/sdk/idle`), `pub` (`[{ event, auth, auth-users }]` or bare names), `sub` (`"site:event"`, events.ts), `service`. `publishEvent` fans out to `subscribersOf` (current manifests, `eventAccess` = that event's entry in the publisher's `pub`: `subAccess` in events.ts, `none` | `lax` (owner + `auth-users`, the default) | `strict` (those users and a per-event approval in `subClients`, set by the publisher over `/runtime/sub-clients`; never `publish` or superuser). A subscriber that isn't allowed still starts and learns it from `subscriptionStatus` (first stream line, `/runtime/subscriptions`); it never starts, holds or is woken by the publisher: a server gets NDJSON over `GET /runtime/events` (queued in `EventQueue` and `spawnProcess`ed when stopped), a function gets a one-shot `fn-host.ts <entry> --event` run per event (`runFnEvent`, retries `EVENT_RETRY_DELAYS_MS`, the event in the runtime record). Subscribers hold publishers through `liveSubscribes` in `heldBy`, but `stopDependents` walks `dependentsOf` (depends only), and `startPublishers` is not awaited, so circles are fine. `to` (`publishTargets`, `strict` events only; `/runtime/publish` refuses it on `none`/`lax` and on bound entries) narrows `publishEvent` to named subscribers and throws (409) when one isn't in `subscribersOf`. Delivery is one queue per subscriber (`EventQueue` in events.ts: `push`/`take`/`done`/`fail`/`release`; bookkeeping only), each waiting event a file under `EVENT_QUEUE_DIR` (`<state>/events/<sub>/<seq>-<id>.json`, restored by `loadEventQueue` at the end of startup). `pumpEvents` hands out: functions up to `FN_EVENT_CONCURRENCY` runs, servers over a `?ack=1` stream, answered by `POST /runtime/ack` (`settleEvent`; `EVENT_ACK_TIMEOUT_MS`; a stream without `ack=1` is settled on write). Failures retry on `EVENT_RETRY_DELAYS_MS` then drop; a closed stream `release`s (no attempt counted). `ordered` on a `pub` entry (`eventOrdered`) serialises that publisher:event per subscriber, unless the subscriber's entry ends in `:unordered` (`UNORDERED`; parsed by `parseSubscription`, stored without the suffix in `sub` plus the key in `SiteManifest.unordered`; there is no `:ordered`). A server stream opened with `?ack=1&parallel=1` (the SDK's `subscribe()`, which runs handlers without awaiting the previous one) gets up to `SERVER_EVENT_CONCURRENCY` events at once; a plain `?ack=1` stream still gets one at a time. Inbound: `"*::<event>"` in a receiver's `sub` (`ANY_SITE`, `inboundKey`, parsed by `parseSubscription`) plus a sender's bound entry `{ event: "<bind>:<name>", bind }` (stored as `PubEvent` with `bind`, auth `none`; no auth keys allowed); `/runtime/publish` passes `rules.bind` and `publishEvent` delivers to that site alone as event `<name>`, refusing when it lacks the `*::` entry. Every app event carries `sender` (`EventSender`: name, user, kind, url), built from the grant in `/runtime/publish`, never from the body. Never audit event data. Built-in events come from the reserved site `candy` (`BUILTIN_SITE`, `BUILTIN_EVENTS` in events.ts; manifest.ts refuses an unknown one; `checkSubscriptions`/`subscriptionStatus` skip them): `candy:sub-request` is sent by `announceSubRequests` (from `applyManifest`, for the site read and the publishers it subscribes to) to a publisher that lists it in `sub`, once per pending app+event (`subRequestsTold`, memory only). Service tokens (`service-auth.ts`, header `Candy-Service-Token`, `typ: candy-service`, 5 min) are sealed with the target's key from `serviceKeys` (its own `AppKeyStore` file, never the sign-in ring) and say `app` + `user` of the caller's grant, never a person.
- **Alarms and soft crons** (`alarms.ts`, SDK `setAlarm` / `setCron` / `cancelAlarm` / `listAlarms` / `onAlarm`, `alarmOf` for functions): no candy.json entry. `POST /runtime/alarms` (`action` list | set | cancel; set takes `at` / `in` or `cron`, plus `data` ≤ `MAX_EVENT_BYTES`) from any launch of the site; a function whose `handlers` leave out `"sub"` is refused. `AlarmStore` keys by site + user (the name in other hands starts empty), `MAX_ALARMS` per site, one namespace for both kinds; persisted to `<state>/alarms.json` (`saveAlarms`, atomic). One timer (`scheduleAlarms`, re-armed at least hourly) runs `fireAlarms`: `takeDue` drops a one-off, moves a soft cron to its next run after now (`cronNext` in cron.ts; missed runs collapse into one), and each due alarm becomes a `candy:alarm` event (`ALARM_EVENT`, from `BUILTIN_SITE`, data = the `Alarm`) handed to `deliverEvent` for that site *before* the file is saved (at least once). It then follows the normal queue: wakes a stopped server, acks, retries, `QUEUE_TTL_MS` from fire time. At startup `fireAlarms` runs after `loadEventQueue`. `dropAppAuth` drops the site's alarms. `candy:alarm` is not a `BUILTIN_EVENTS` entry: manifest.ts refuses it in `"sub"` with a pointer to the SDK. `/runtime/events?alarms=1` (sent by the SDK when an `onAlarm()` exists) skips the "subscribes to nothing" 403. The SDK keeps **one** stream per runtime (`listen` in sdk-runtime.ts; the daemon writes each event to every stream of a site), routes `candy:alarm` to `onAlarm` handlers (else `subscribe` ones) and the rest to `subscribe` ones; an event nobody in the process takes is acked as failed. `/configs` carries `alarms` (name, at, cron, setAt; never data) for the Manifest tab's *Alarms and soft crons* section. `alarms.ts` is part of the function shim (install-service.sh).
- **Certificates per name**: every Caddyfile block that answers many names (the `*.candy` / `*.localhost` catch-alls, the `*.kill.` / `*.k.` / `*.portal.` / `*.p.` shortcuts, the alias host lists) uses `TLS_PER_NAME` (caddy-config.ts: `tls internal { on_demand }`), so Caddy's internal CA issues one certificate per exact name at its first handshake, never a wildcard or a multi-name one. No `on_demand_tls` ask endpoint: the issuer is internal only. So does every named block (`name.localhost`, `name.candy, alias.candy`): next to an on-demand wildcard Caddy manages no certificate for a name the wildcard covers, and plain `tls internal` there fails the handshake (alert 80). No block may use plain `tls internal` (test/tls-per-name.test.ts). Caddy serves a stored wildcard for any name it covers before issuing a per-name one, so `purgeSharedCerts` (in `startCaddy`, before the spawn) deletes stored leaf certificates that are wildcards or name several hosts (`isSharedCert`; never `pki/`); `name.candy, alias.candy` blocks just get theirs issued again.
- **One root for the network** (caddy-config.ts "One root"; daemon.ts `candyHub`): `advertiseToHub` resolves `candy.candy` and calls `setHubRole`: `hub` (it is this machine), `peer` (another tailnet IP) or `none`; a change runs `syncCaddy`. **Hub**: `hubSiteBlock` writes a `candy.candy` block whose `/acme/*` is Caddy's `acme_server` (`tls-alpn-01` only, `lifetime` `HUB_CERT_LIFETIME`, `allow { domains … }` from `hubAllowedDomains(hubHostLabels())`: smallstep's `*.` is one label deep, so every shape and every host label is listed; a new label from `/candy/advertise` triggers a sync via `hubLabelsWritten`), the rest to the daemon. `GET /candy/ca/root.crt` serves Caddy's root (`caddyRootCertPath`), hub only. **Peer**: `pinHubRoot` fetches that over `http://<hub>:9999`, checks it is a CA certificate, and pins it in `HUB_ROOT_FILE` (`~/.config/candy/hub-root.crt`); a different root later is logged (`HUB_ROOT_CHANGED`) and ignored. With it pinned, every `*.candy` block uses `candyTls` = `tlsFromHub(HUB_ROOT_FILE)` (on-demand, `issuer acme` at `HUB_ACME_DIRECTORY` with `trusted_roots`, then `issuer internal` as fallback); `*.localhost` blocks always use `TLS_PER_NAME`. The validation is the DNS: the hub connects to the name, which its own DNS gives to the machine that advertised it. **Everywhere**: the global block has `pki { ca local { intermediate_lifetime 30d } }` and `on_demand_tls { ask TLS_ASK_URL }`; `GET /candy/tls-ask?domain=` (loopback only) answers by `servesHost` (any `*.localhost`; of `*.candy` only own sites, reserved names, their host-label and shortcut forms), so an unknown `.candy` name fails the handshake. `refreshShortIntermediate` (in `startCaddy`) deletes an intermediate made for less than 30 days so Caddy makes a new one under the same root; never the root. test/one-root.test.ts runs a real hub and peer Caddy in `unshare -Urnm` with `/etc/hosts` as the DNS.
- **Sign in with candy + passkeys** (`SDK_AUTH_DESIGN.md`): apps send the browser to `/app-auth/authorize` (public, portal only: `validateAuthorize`, `return_to` exactly `https://<site host>/_candy/auth/callback`, parked as a sealed stateless id (`sealed-ids.ts`), never a redirect on error); the consent page and `POST /app-auth/decision` (page token) mint a one-shot JWE (`jwe.ts`, `dir`+`A256GCM`, per-site key, `aud`=site, `dest`=exact callback, which the SDK compares with the URL the token arrived at, never the state cookie) that goes back as a form POST, never in a URL. A rotated-out key travels in the ring with its `retired` time and opens only older tokens. Route logic lives in `app-auth-routes.ts` (deps injected; `test/app-auth-flow.test.ts` drives it end to end), stores in `app-auth.ts` / `passkey-store.ts`, WebAuthn in `webauthn.ts`, the app side in `sdk-auth.ts` (`sdk.ts` `appAuth()`, functions' `env.CANDY_AUTH`). Site keys reach launches as `LoadCredential=` (sandboxed) or spawn env, **never argv** (`SECRET_ENV_NAMES` in sandbox.ts); `/sdk/auth/keys` is the owner's API key only (`mayFetchSiteKey`). `POST /app-auth/drop` revokes a ring and the site's approvals outright (`keysDropped` removes the credential file); `/app-auth/sites` reports `enabled` (the site still asks: `isAuthSite`). `/settings` and `/passkeys` are portal SPA pages (`web/src/pages/settings/`, app routes). Tokens carry `superuser` (`isSuperuser` at mint time) and `auth_time`/`amr` of the session's latest authentication (`authAt`/`authMethod`, portal-session.ts). `max_age` (0..86400) is parked with the request; when the login is older (`freshnessOk`, app-auth.ts), the decision is 401 until the user authenticates again for that request (`/app-auth/fresh` passkey hop, or `/auth/reauth {request}`), bound by `freshFor` = `freshKey(request id)` and used up by the mint; the SDK keeps `maxAge` in its own state cookie and refuses older tokens (`stale_auth`).
- **Passkeys live on candy's own host** (`candy.<zone>`, `candyHost()` in daemon.ts; candy-host.ts; SDK_AUTH_DESIGN.md "G"): the portal hosts use Caddy's local CA, and browsers refuse WebAuthn behind a certificate error, so the rpId is always the candy host and every ceremony runs there. No bound domain (zone + tunnel): no passkeys (the routes 404, the UI says why). The host serves only `CANDY_HOST_ROUTES` (page, options, verify for `enroll` and `login`), each needing a **stamp** (`PasskeyTickets`, sealed, single use, 5 min) minted on a portal host (`/auth/passkey/start`, `/passkeys/enroll/start`, `/app-auth/fresh`) and claimed by the first browser that opens it (`CEREMONY_COOKIE`); everything else there is 404 (or the public MCP paths when `domainConfig.mcp.subdomain` is `candy`). It never reads portal cookies, API keys or `X-Candy-Session`. A login ends with a one-time code (60 s, `PASSKEY_BIND_COOKIE`-bound, its own portal host) that the page form-POSTs to `/auth/passkey/finish` (TOKENLESS; Origin must be exactly `https://<candy host>`, `fromCandyHost`), which makes the session (`amr: "passkey"`) and hands the secret to localStorage through a tiny page, never a URL. Enrolling needs a recent password (`mayManagePasskeys`) and the stamped portal session still live. `candy` is a reserved subdomain (`checkBindings`, `/domains/bind`); the daemon adds its Caddy block, ingress and DNS (`ensureCandyHostDns`) itself, and prunes passkeys of another rpId (`PASSKEY_DROP`). The old per-portal-host routes (`/auth/passkey/options`, `/auth/passkey`, `/passkeys/register*`) are gone. Never log or audit a token, key, state, password, stamp or login code (Caddy drops `candy_stamp`/`candy_code` query params).
- **Public MCP**: a grant records the approving `user` (mcp-oauth.ts); `handlePublicMcp` runs mcp.ts inside `publicMcpUser.run(user)` and `userScopedFetch` gives its daemon calls that user's key. Grants without a user are revoked on load (`legacyRevoked`, audited).

## Multi-user and API mode

- The systemd unit runs the daemon as root with `CANDY_OWNER=%i`. Members of the `candy` group get per-user secrets; servers run as the user who registered them (`ServerConfig.user`, launched with `setpriv`). Never start anything as root. See `launchSpec`, `requestAuth`, `mayChangeConfig` in daemon.ts.
- Per-user authorization: everyone sees and changes only their own sites; a superuser (a sudoer, logged in to the portal; never the CLI/SDK/MCP) sees and manages everything and changes daemon-wide settings. Running a site as another account is portal-superuser only; API keys run as themselves.
- Root mode launches go through `systemd-run` (`sandbox.ts`, `launchSpec`): read-only filesystem except the code folder, `/var/lib/candy/<name>` and a private `/tmp`; unit bound to the daemon's unit. Stop with `systemctl stop <unit>` (`managed.unit`), not a process-tree kill. `ServerConfig.sandbox === false` opts out; `ServerConfig.rw` adds writable paths. Every unit gets `MemoryMax` and `MemoryHigh` at 90% of it (`memoryProperties`; 2G default, `ServerConfig.memory` in MB up to 16G, `candy mem`; `memoryLimitMb` in sandbox.ts caps it).
- `ServerConfig.api`: every request for the server's host (bound domain, `<name>.localhost`/`.candy`), whatever its method or path, is held while a stopped server starts and forwarded 1:1 (`api-mode.ts`, `apiModeGate`), never a loading page or a daemon route. The gate runs in `controlFetch` before anything that matches a path; keep it there (`test/api-mode.test.ts`). Failures are 503 + `Retry-After`. Only `/candy-auth/check` and `POST /candy-auth/login` on a protected bound domain stay candy's.

## System monitor

`sysmon.ts` (parsers + `SystemMonitor`) reads /proc for the whole machine; `/system/stats`, `/system/kill`, `/system/unit` in daemon.ts are class `superuser` and also check for a portal login (never API keys or OAuth tokens). Actions run as the daemon (root): keep `killProblem` / `unitActionProblem` in front of them, and never add a route here that takes a command or a path.

## Public MCP endpoint

Optional (`domainConfig.mcp`, off by default; the default subdomain `candy` shares candy's own host, where only `isPublicMcpPath` paths go to MCP): `https://<sub>.<zone>/mcp` serves `handleRequest` from mcp.ts over HTTP behind OAuth 2.1 (`mcp-oauth.ts`, pure logic). Consent happens only on the portal host (`/oauth/*`, tailnet) and needs a portal login; tokens act as the approving user, user-scoped. See `handlePublicMcp` in daemon.ts. The public host must never reach any other daemon route.

## Reserved Names

Cannot be used for server names: `portal`, `p`, `kill`, `k`, `candy`, or anything starting with `_` or `.`. The bound-domain subdomain `candy` is candy's own host and can't be bound. A new name also can't have a `kill`/`k`/`portal`/`p` label or end in `.<hostLabel>` (`newNameProblem`): those are shortcut and alias hosts.

Names are lower case. `lowerRequestNames` lower-cases `name`/`oldName`/`newName`/`serverName`/`targets` in bodies and `?name=` for every control route, path names are lower-cased where they're read, and `isSafeName` accepts lower case only. Stored names are lower-cased at load (`lowerCaseNames`, `NAME_LOWERCASED`); when two spellings meet, the first in the file stays and the others are dropped (`NAME_DROPPED`).

## Dependencies

Runtime: Bun, Caddy. Optional: `cloudflared` (tunnels), `ripgrep` (log search).

No external npm packages for the daemon, CLI, SDK and MCP: pure Bun stdlib. The one exception is `web/` (the portal SPA), a separate package (not a workspace) with react and react-dom as build-time deps, built to `web/dist` by the owner (`bun run web:build`; `web/dist` is not committed) and served by the daemon.
